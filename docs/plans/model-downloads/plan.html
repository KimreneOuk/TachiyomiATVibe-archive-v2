On-demand model downloads & deletion

TachiyomiATVibe · plan draft for discussion · Nov 2026 · prepared by GLM 5.3 Flash agent · plan target: private KimreneOuk/TachiyomiATVibe-archive-v2 main @ 2c096416 (cached locally as archive2/main)

Draft — decisions pending. UI direction is now set by the user: inline model management in each Translation settings section, no reader-overlay controls, contextual reader download pop-up (§6). Everything under “Proposed” is a recommendation for confirmation; §8 lists the decisions that must be settled before tickets are cut. Exploratory UI: canvas “Model manager UI”. No code has been changed.

1 · Goal

Model binaries are not committed to the repository at all — they are provisioned onto the build machine into app/src/main/assets/models/ by scripts/fetch_models.py + scripts/models.manifest (19 files, ~713.6 MB manifest-guaranteed) before Gradle packaging, so a release APK normally carries them as packaged assets. A further ~225 MB of unmanifested files (LiteRT vision overlays, legacy AOT ONNX pair) can end up in an APK only when someone provisioned them by hand on the building machine — that is machine state, not repo state. The goal: keep only the essential set present by default and let the user download or delete every other model family on demand — safely, verifiably, and without breaking any pipeline route.

Essential set (user-defined, ~29 MB total — a proposed future default, not present behavior): comic text/bubble detector, manga panel detector, bubble segmenter, PaddleOCR ONNX (recognition + dictionary + detector). Today only the detector is hard-required at init; panel, segmenter, and Paddle degrade gracefully when absent, and Paddle is selected by no default route on any language — its essential status is the user's request for this system, to be implemented, not a current fact.

Key constraint surfaced by this audit: anything that stays packaged inside the APK cannot be deleted by the user to reclaim storage. Deleting runtime copies frees app data, but the packaged assets remain part of the installed app forever. “Download & delete” only truly applies to families that are not in the APK — see tradeoffs (§7) and D1/D4.

Hidden dependencies & “presence ≠ route” findings (11)
  1. ensureModels() eagerly copies ~110 MB usually unused: the MangaOCR quartet for every user (incl. ML Kit/Paddle, non-Japanese) plus aot.onnx+aot-512.onnx (46 MB) that no production code reads — biggest on-demand win and the mandatory-init blocker.
  2. aot.onnx, aot-512.onnx, detection/litert/detector_v4_s_fp32.tflite (169.6 MB!), detection/litert/panel_detector_fp32.tflite are bundled but absent from models.manifest — untracked, unhashed, invisible to integrity tooling.
  3. ocr/paddle-v6-small/inference.json (208 KB) is referenced by no code and no script — orphan.
  4. assetsAvailable() treats “models/ocr OR models/detection” as available — a partial asset set passes the probe and fails later at init.
  5. Cache validity uses <name>.version stamps + MODEL_ASSET_VERSION and a looksLikeValidOnnx heuristic; the download system must keep stamp semantics or it will fight this cache.
  6. “Store-preserve” semantics: when an asset is absent, the store deliberately keeps an existing cached copy (“preserving existing cached…”). Downloads must slot in ahead of, not behind, this rule.
  7. LiteRT “vision” probes (segmentation/litert/*, ocr/litert/*) log INFO “not bundled” every init — phantom expectations that never resolve.
  8. Paddle det is loaded even for non-Paddle users (free-text erase); its absence is a silent capability downgrade, never blocking.
  9. Colorization/upscaling engines are constructed eagerly at TranslationManager creation but only probe assets at isAvailable() — absence is silent; the reader-side toast covers inpainting only.
  10. Fumeto sessions are lazy “so pipeline startup stays free of the ~450 MB model” — a precedent for download-on-first-use.
  11. Device-selection claims need code + runtime evidence, not docs. docs/MODEL_SOURCES.md says the Paddle LiteRT graphs “support the saved GPU/CPU device choice and temporary reader override”, but at 2c096416 no persisted selector and no reader-side Paddle provider override were traced into RoiVisionEngineFactory: the ONNX path requests QNN GPU by a hardcoded constant, the LiteRT path passes preferGpu=true with XNNPACK fallback, and PaddleOcrProviderOverride is device policy, not a user control. Actual backend execution on a device is knowable only from runtime logs (executionProviderLabel) or device testing — the download system's UI must not present a saved CPU/GPU picker unless such a selector is built.

5 · Proposed design

5.1 Components

  • ModelCatalog (new, eu.kanade.translation.models.catalog): single source of truth in-app — per family: id, display name, role (ESSENTIAL / OCR_MANGAOCR / OCR_PADDLE_LITERT / INPAINT_* / TRANSLATE_FUMETO / COLORIZE_FFDNET / …), files (path, bytes, SHA-256, URL), requiredBy (routes), license + source labels. Families include every target-repo consumer, FFDNet included. Mirrors scripts/models.manifest; long-term, the manifest itself ships as a resource to avoid a second copy drifting.
  • ModelInstallRepository: resolves status per family — NotInstalled / Installed / Downloading / Failed — with resolution order: runtime dir → APK asset → absent. Keeps the existing stamp files and noBackupFilesDir/tachiyomiat-models/ layout so bundled-copy logic is unchanged; adds a parallel “downloaded” provenance mark.
  • ModelDownloadManager + WorkManager ModelDownloadJob: foreground CoroutineWorker modeled on AppUpdateDownloadJob (OkHttp newCachelessCallWithProgress, throttled notifier, Constraints(CONNECTED)), Wi-Fi gating via the existing pref_download_only_over_wifi_key pattern, sequential queue, disk-space guard (200 MB precedent from Downloader), tmp file + atomic rename + SHA-256 verify before publish, per-file resume/restart, auto-retry on transient failure.
  • ModelDeletionUseCase: refuses deletion while a family is mapped by an active EngineLane/session (offers queue-after-session), refuses or warns for essentials (decision D4), clears stamps, and resets any pref whose selected route required the family (with the visible checkbox from the mockup) — for FFDNet specifically this includes prefer_ffdnet_denoising, because a deleted model with the pref left ON makes every colorize pass fail loudly (colorization FAILED), not silently bilateral (§3.2).
  • OnnxModelStore refactor (the load-bearing change): split ensureModels() into per-family guards; MangaOCR copy becomes conditional + MangaOcrEngine reports unavailable instead of throwing; OcrModelCatalog coercion only picks installed models (UI already shows availability); remove the dead aot.onnx/aot-512.onnx copies; keep the legacy asset-fallback path for one release (migration), then asset → download-only per family.
  • Reader gating: extend the existing ReaderTranslationController.inpaintModelMissing() pattern — selected-but-missing models surface the contextual pop-up (download & continue / continue without / cancel); a missing essential shows a blocking banner. The reader overlay itself carries no management controls — selections only (user direction). Mirrored toasts for colorization/upscaling absence if those routes ever ship assets.
  • Notifications: new GROUP_MODELS + CHANNEL_MODEL_DOWNLOAD_PROGRESS (low importance) in Notifications.kt, following the GROUP_TRANSLATION precedent.
  • Storage accounting: model dir size surfaced via DiskUtil.getDirectorySize — inline near the feature sections that own the models, with an optional aggregated row in Settings → Data & storage next to “Clear chapter cache”.

5.3 Upgrades & migration

  • Catalog carries a per-file version alongside its hash; on app update, changed catalog entries re-copy (bundled) or re-download (remote) only the changed files — mirroring today's MODEL_ASSET_VERSION stamp bump but per family.
  • First run after adopting this system: essentials come from APK assets (if still bundled) or queue a one-time essential download; no user interaction needed beyond Wi-Fi policy.
  • Hygiene sweep (same release): stop bundling aot.onnx/aot-512.onnx (46 MB, verified at 2c096416: copied at ensureModels(), only consumer is the debug QnnDiagnostics) + orphan inference.json, and prune their stale cache copies via the manifest's --clean semantics. Add manifest entries for FFDNet and the LiteRT vision overlays (hash them) even if they stay locally provisioned — provisioning and integrity tooling currently can't see them.

6 · UI/UX direction (set by the user)

User preference, superseding the earlier “dedicated manager” recommendation: model management lives inline within each existing Translation settings feature section (translation, cleaning/inpainting, OCR, colorization, upscaling — each feature’s models surface next to that feature’s controls). The reader overlay carries no model-management controls; a contextual reader pop-up offering to download a missing model when needed is welcome. The canvas is being updated by the requester to this direction.

6.1 Placement per existing section

  • OCR group (getTranslationLangGroup in SettingsTranslationScreen): the per-language OCR model picker rows gain availability state — “MangaOCR · not downloaded · 65 MB” with an inline Download action; installed models get an inline Delete affordance with the confirmation dialog.
  • Cleaning / inpainting group (getInpaintingModeGroup): the FAST/BALANCE/QUALITY tiles stay; the neural-model row (LaMa / AOT) shows availability + Download/Delete inline.
  • Engine / translation group (getEngineGroup): the Fumeto engine row shows “not downloaded · 452 MB” + Download inline when selected-or-selectable.
  • Colorization group (getColorizationGroup): FFDNet toggle sits beside its availability + actions (target-repo family); colorization model rows likewise.
  • Upscaling group (getUpscalingGroup): artifact status inline (hidden or “unprovisioned” until artifacts ship).
  • ML Kit: shown as “provided by Play services” — never a download/delete item.

6.2 Reader behavior

The reader settings overlay keeps selections only (modes, models, languages) — no download/delete controls there. When a translation starts and a needed model is missing, the contextual pop-up offers it: “Download & continue · 3.3 MB / Translate without it this time / Cancel”, extending the existing inpaintModelMissing() gating; a missing essential shows a blocking banner instead. Fallback policy for “continue without” remains an open decision (D5).

6.3 Consequences of the inline direction

  • Per-file detail (integrity, hash, source, used-by) has no dedicated screen — it needs a lightweight inline treatment: an expandable row or a details dialog opened from each model row. Presentation detail, to settle in tickets, not a direction change.
  • Download progress renders inline in the owning section (progress bar on the row, pause/cancel), mirroring the downloading-card state from the canvas.
  • An aggregated “storage used by models” figure can still surface in Settings → Data & storage next to “Clear chapter cache” if wanted — optional, not required by this direction.
  • Both directions remain mocked in the exploratory canvas for reference; Option A is no longer the recommendation.

7 · Tradeoffs

  • Bundled essentials cannot be deleted to reclaim storage — the core tension with the stated goal. Assets packaged into the APK are part of the installed app for its lifetime; deleting runtime copies or caches never shrinks the install. So every family kept in the APK is exempt from the user's “download & delete” goal by construction, and every family moved to download-only becomes reclaimable but costs network at first use (and must be re-fetchable — see §4's publishing gap). This is unresolved by design: it is D1/D4, not a detail.
  • APK size vs first-run bandwidth. Slimming to essential-only (or asset-free) cuts the install by hundreds of MB but makes first translation require downloads over Wi-Fi. Keeping essentials bundled keeps “works offline, immediately” but locks in their install-size cost. (Decision D1.)
  • The ~169.6 MB GPU detector overlay (locally provisioned, unmanifested) is the single biggest file in the build directory. Dropping it loses the LiteRT GPU detect route (ONNX stays authoritative); publishing it as an optional download keeps the route but adds release/hosting work. (Decision D2.)
  • Hosting & rights. The public KimreneOuk/TachiyomiATVibe repo already hosts two releases; archive-v2 (the target repo) is private and hosts none. Choosing where runtime downloads come from is a project decision, and publishing the converted essentials additionally awaits the unresolved rights determinations recorded in the repo docs — no permission is assumed either way. (Decision D3.)
  • Relaxing MangaOCR init touches the most fragile init path in the pipeline; the refactor must preserve today's failure semantics for truly-required files while adding unavailability for optional ones. Mitigated by keeping the ONNX store's stamp/validation machinery untouched.
  • ML Kit is out of scope by nature — it must not appear as a deletable/downloadable item, and UI copy should say why. FFDNet exists only in the target repo; if the later branch ever becomes the base, that family disappears from the catalog rather than being “uninstalled”.

8 · Decisions needed

Settled by the user: UI placement — inline management per feature section, no reader-overlay controls, contextual reader download pop-up (§6). Still open — policy, not placement: bundled vs download-only essentials and the storage-reclaim tension (D1/D4), actual fallback policies when a selected model is absent (D5, plus FFDNet's fail-loudly semantics), and distribution host/publication with the unresolved rights determinations (D2/D3).

D1 · APK slimming strategy — with its storage-reclaim consequence

Keep essential 29 MB bundled (offline-ready, but permanently exempt from delete-to-reclaim) vs slim APK so essentials are download-only (reclaimable, but first use needs network and a published release must exist). Middle option: bundled now, asset-free packaging later. Recommended: keep essentials bundled for v1, revisit asset-free packaging once releases exist — but this cannot give essentials the delete-to-reclaim property; that only comes with download-only.

D2 · Fate of the ~169.6 MB LiteRT detector overlay (+ panel fp32)

Drop (GPU detect route lost, ONNX authoritative) / hash + publish as optional download / keep hand-provisioning. Recommended: publish as optional download; keep out of packaging.

D3 · Distribution host & publication of missing artifacts (separate from rights)

Where runtime downloads come from (public TachiyomiATVibe releases vs the private archive-v2) is a hosting choice. Publishing the two converted essentials and the overlays additionally requires the rights determinations below — until both are made, those families must stay build-time-bundled or simply be non-restorable after deletion. Needed from you: host choice, and go/no-go on seeking the rights determinations. No permission is assumed.

D4 · Deletability & rights determinations for panel/bubble derivatives

Two coupled questions: (1) UX — if bundled (D1), essentials are non-deletable with a visible “restore” instead of “delete”; if published, they become deletable with re-download. (2) Rights — the repo docs record unresolved AGPL-treatment (panel) and Manga109 terms (bubble); a determination is required before any publication, and this plan does not presume its outcome.

D5 · Behavior when a selected OCR model is absent

Coerce to a fallback with a notice / block at reader with the pre-flight sheet / block at settings. Recommended: coerce in settings (visible chip), pre-flight sheet in reader.

D6 · Fumeto (452 MB) download trigger

Auto-queue when the Fumeto engine is selected / require explicit download first. Recommended: explicit download; selection shows “not installed” and the reader sheet offers it on first use.

D7 · Delete-vs-active-session policy

Hard block while any inference session maps the family (queue after) vs copy-on-write. Recommended: hard block + queue.

D8 · Dead-asset & manifest hygiene in the same release

Stop copying aot.onnx/aot-512.onnx (46 MB production-unused — verified at 2c096416) and the orphan inference.json; add manifest entries (hashes) for FFDNet and the LiteRT vision overlays so provisioning/integrity can see them. Recommended: yes.
